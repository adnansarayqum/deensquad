# Deen Squad parent app

Mobile web app (installable PWA) for The Deen Squad Football Academy. Parents sign in by email, read club news and tap to acknowledge it, say whether each child is coming to the next session, finish a per-child checklist and follow each child's progress. Coaches use a gate register. Admins import families from a CSV, send invites, post news with read receipts (and chase on WhatsApp), schedule sessions and manage staff. Data lives in Postgres (Railway in production).

| Apply migrations to `DATABASE_URL` | `npm run db:migrate` (Railway runs it before every deploy) |
| Regenerate design tokens | `npm run tokens` |
| Rebuild the offline QR page script | `npm run offline` (writes `public/offline-pass.js`; bump `VERSION` in `public/sw.js`; `src/offline/build.test.ts` fails while it's stale) |

Railway (project `deensquad`: services `parent-app` + `Postgres`, both in San Francisco) builds it, runs `scripts/migrate.mjs` at container start (before `next start`; a failed migration fails the health check and the old version keeps serving); settings in `railway.json` override the dashboard; Node is pinned by `engines` in `package.json` to `>=22.13 <23`. Live at https://app.thedeensquadfootballacademy.co.uk (DNS at IONOS: CNAME `app` → Railway; the old parent-app-production-4b29.up.railway.app address still works) |

Before committing: `npm run typecheck && npm run lint && npm test`, and `npm run test:e2e` when screens or actions change. Stop any running `next start` before `npm run build`; rebuilding under a live server serves mismatched chunks.

## Architecture

- **Database:** `db/migrations/*.sql`, applied in name order, each once (`scripts/migrate.mjs` on Railway, `src/lib/db/migrate.ts` locally). Never edit a migration that has been deployed; add a new numbered file. Both runners set `lock_timeout = '5s'` inside the migration transaction, so a migration that would wait on a busy table fails fast (non-zero exit, nothing applied) and can simply be rerun. Migrations are forward-only (e.g. 0014): to back a feature out, roll back the code, never the migration; undo schema with a new numbered file. `0001_auth.sql` is a Supabase-shaped auth schema (`auth.users`, `auth.uid()`, sign-in requests, sessions). `0002_club.sql` is the club schema with row level security.
- **Security model:** the app connects as the DB owner. `asUser(userId, fn)` (`src/lib/db`) opens a transaction, sets `app.user_id` and `set local role authenticated`, so every policy applies. `asSystem` bypasses RLS and is only for sign-in/sessions/invites. Parent writes that touch `players` or `payment_status` go through security-definer functions (`set_photo_consent`, `report_payment_setup`); the squad headcount comes from `squad_counts()` so parents never read other families' answers. `staff_names` exposes staff names without emails.
- **Multi-child:** `player_guardians` is many-to-many. Parent queries must filter to `my_player_ids()` / the family's age groups explicitly, because a parent who is also staff can read the whole club under RLS.
- **Drivers:** `DATABASE_URL=postgres://` uses postgres.js; `pglite://memory` or `pglite://<dir>` uses PGlite. Both behind `Database`/`Queryable` in `src/lib/db/types.ts`. Cast enums/arrays to text (`::text`, `::text[]`), counts to `::int`, dates to `::text` in selects so both drivers return the same shapes. `DEV_SEED=1` seeds the sample club (refused on Railway).
- **Auth (`src/lib/auth`):** email with a 6-digit code + single-use link (hashed in `auth.sign_in_requests`, 15 min; invites 7 days, link only). The code exists because iPhone home-screen apps don't share cookies with Safari. The link page needs a tap (email scanners). Unknown emails get the same screen and no email. Rate limits (`LIMITS` in `service.ts`): 5 codes per email and 100 per IP an hour (venues share wifi), and at most 300 sign-ups (requests with `registration`) an hour club-wide, which refuses with the same screen and sends an error alert; ordinary sign-ins never count towards that cap. The IP is `x-real-ip` (set by Railway's edge), else the rightmost `X-Forwarded-For` hop (`src/lib/auth/ip.ts`). Sessions: random cookie `ds_session`, SHA-256 in `auth.sessions`, 90-day sliding. `src/proxy.ts` only does the optimistic cookie check; pages call `requireParent/requireStaff/requireAdmin` (`session.ts`). `ADMIN_EMAILS` creates the first admin on sign-in.
- **Email (`src/lib/email`):** Resend over HTTPS when `RESEND_API_KEY` is set; otherwise an outbox file in dev/tests. In production without a key, only admin sign-in emails are printed to the log (parents' count as not sent). `sendEmails` never throws: it returns `{ sent, failed }` per 100-email Resend batch (10 s timeout, `SEND_TIMEOUT_MS`), so callers must check `failed`. A caller can give an email an `idempotencyKey`; only then is Resend sent an `Idempotency-Key` (`requestKey`: the key itself for one email, a hash of the keys in order for a batch whose emails all have one). The chase ladder's reminder emails use `<announcement>:<guardian>:email`, so a later run retrying one that timed out but went can't email that parent twice (Resend keeps keys 24 hours); a 409 on a keyed request counts as already sent. Other callers give none. A batch's key only matches when the same parents are in it, so a run whose list has changed is protected only for single sends. Bulk invites go only to not-yet-invited parents with a child in the Families list as filtered (`group`/`need`/`q`, via `familyWhere` in `src/lib/admin/data.ts`, shared with the list and the banner's count `countUninvited`), and only from the confirmation page `/admin/families/invite` ("Email 12 parents in U12?" / "Email all N parents in the club?"; a plain form sending `confirm=yes`, else `inviteParents` redirects there). Invites mark `invited_at` (and keep the link) only for parents actually emailed; the admin sees "Sent to N. M not sent – try again later." and a retry reaches only the rest. A failed new-order email clears `notified_at` so the next call retries. The sign-in email leads with the code; the link is the alternative (using either spends both).
- **Parent screens:** `src/app/(parent)/` (news, friday, checklist + contacts/payment/consent, player). A child's "next session" is the first one that isn't cancelled (`nextSessionFor`); cancelled ones before it show on Friday as "Cancelled: <title>, <day>" with the reason (`ChildWeek.cancelled`), so a cancellation never hides the next question, plan or headcount. Session `notes` show in the Friday briefing, Coming up and squad invites. Loaders in `src/lib/parent/load.ts`, queries in `data.ts`, pure view builders in `views.ts`, actions in `actions.ts` (call `refresh()` after in-place writes). To-do (`/checklist`): per child, registered, emergency contacts ("Also add for" siblings) and photo consent ("Same for all my children": siblings without an answer are ticked, those with one show it unticked); for the whole family (`buildFamilyChecklist`, a "Whole family" section, or merged into the list for one child), the monthly plan and the contract. The payment step is family-level: `/checklist/payment` shows `CLUB_FEE_TEXT` (else "Ask the club about fees"), and one "I've set it up" ("Covers Yusuf, Ali and Maryam") calls `report_payment_setup` for each child whose plan is missing or overdue (`reportFamilyPayment`); without `TEAMFEEPAY_URL` the button isn't offered ("The club will tell you how to pay") and the action refuses. Admin payment status stays per child. Forms using `useActionState` keep `action={run}` and add `onSubmit={submitKeepingInput(run)}` (`src/components/submitKeepingInput.ts`): React 19 otherwise clears an uncontrolled form even when the action returns an error. Those forms clear themselves on success (`StatefulForm` after any result without an error). Friday shows who gave each answer (`answeredLine` in `views.ts`: "Coming · answered by Sara, Tue 2:02pm", "you" for the viewer, no name for an answer without `availability.answered_by`, which `saveAnswer` sets, or by a guardian no longer linked to the child); the picker's "Saved…" line is only for the person who just tapped. A chosen "Not this week" is neutral (ink border on cream), not kit-orange: it's a finished answer. Friday's briefing (and a squad invite) has the venue with a 48px "Directions" link (`directionsUrl`: a Google Maps search, `target="_blank" rel="noopener"`; none for "to be confirmed"/TBC). News "I've read this" buttons are named "I've read this: <headline>", and after a tap focus moves to that message's card under Earlier (`ReadFocus`). `StatefulForm keepOnFailure="…"` (plan and practice-sheet forms, whose actions don't redirect): a file over 8 MB is refused in the browser naming its size (`fileTooBig`/`oversizeFile` in `src/lib/files.ts`, the server says the same), and a save that throws (no answer, a body over the 9 MB action limit) keeps the text and shows that message instead of the error page. Single-tap actions (Mark here, Undo, Coming/Not this week, I've read this) go through `tapAction` (`src/components/TapProblem.tsx`): a thrown action shows "That didn't save. Check your signal and try again." with Try again beside that row (Next redirects still rethrown); an action that returns `{ error }` (e.g. a session that can't be answered any more) shows its message. These are buttons, not forms, so they need JavaScript, as before.
- **Staff:** `/coach` register (`src/lib/staff`), `/admin` (`src/app/admin`, `src/lib/admin`): CSV import (`import.ts`, preview is a dry run rolled back), invites, news + read receipts + WhatsApp chase (logged in `announcement_chases`), sessions, staff. Sessions (`src/lib/admin/sessions.ts`, migration 0015): Add skips any date that already has a session (cancelled included) with the same start and an overlapping group, and says so ("Added 10 sessions. Skipped 2 that already existed (9 Oct, 16 Oct)."); each session has its own Edit (`/admin/sessions/[id]/edit`: details, briefing and `notes` for parents; changing groups takes children outside them out of its squad with their answers; answers stay when the time moves; optional "Tell the families about this change", unticked), Cancel/Restore (`/cancel`: optional reason in `cancel_reason`, shown to parents and cleared on restore; "Tell the families now" ticked by default) and Delete (`/delete`: says what goes with it, sends `confirm=yes`; never once anyone is checked in) pages, all plain forms with the same coach scope (`within`). Telling the families posts club news via `postSessionNotice` to the session's groups, or its squad (`squad_session_id`) when it has one, with `requires_ack` and `urgent`. Layout (`src/app/admin/layout.tsx`): phones get the pitch header with pill nav (wrapping, never scrolling sideways, so Plans and Points and stars are always on screen); the overview greets staff by their first real name (`greetingName` in `src/lib/greeting.ts` skips Uncle/Coach/Brother/Sister/Aunty/Mr/Mrs/Ms/Miss); at `lg` (1024px) and up a pitch sidebar (`AdminNav layout="sidebar"`) and a `max-w-6xl` main column (forms and detail pages stay `lg:max-w-3xl`). Overview `/admin` is a short, visual dashboard (phone first; at `lg` Needs you on the left, tiles and the chart beside it, then three cards): a greeting with one line ("Fri 9 Oct: 11 of 21 children coming"); the email notice and deletion requests as before; **Needs you**, the only place kit-orange is used, up to 5 rows of a big count + a few words + chevron, each row one 48px link, only items above 0, ranked in `needsYou` (`src/lib/admin/overview.ts`: not answered for the next session when it's today, tomorrow or the day after (London days), overdue, payments to check, paid kit orders to place (admins), parents not invited, missed last 3, parents behind on news (`need=unread`), no payment plan, invited not signed in), else "All up to date.", with "See all to-dos" to Families; four **tiles** (`StatTile`: coming next session with a thin bar, season attendance % with a sparkline of the last 10 sessions, parents signed in, news read % over the latest 3 messages; each a link); **Attendance this season**, one line chart (`AttendanceChart` in `src/components/admin/charts.tsx`, inline SVG + HTML, 0–100%, three hairline gridlines, the latest value labelled at each line's end): a line per group in `chart-1`..`chart-4` tokens (validated with the dataviz palette checker, light and dark) when 2–4 groups have had a register taken, else the overall line in grass; `ChartHover` (client) adds a snapping hairline and tooltip on hover, tap and arrow keys; "Show as table" has every number; **Next session**, one bar per group (coming/not coming/not answered, numbers on the line under it), each linking to that group's register; **Families and payments**, a neutral horizontal bar per To-do step (`HBarList`, of all children, count at the bar's end) and the monthly-plans bar (legend hides parts at 0; overdue is ink, not orange); **News**, the latest 3 ack-required messages as one link each (title, read bar, "17 of 21") and one reminders line hiding channels at 0; **Shop** (admins, only once there's been an order or takings): takings this month and season, and the non-zero order states; spreadsheets folded in a `<details>` at the foot. All numbers come from `loadDashboard` in `src/lib/admin/dashboard.ts` (one `asUser` transaction, limited to `coachLimit` groups; shop figures for admins only; pure view logic in `overview.ts`), every number has words beside it or a table, and every number links to where it can be acted on. Season attendance judges each session against the children in the group that day (`players.joined_on` on or before the session's London date, plus anyone checked in), so an import doesn't lower past percentages; `groupAttendance` (shared with the monthly summary) and the chart's per-session figures (`attendance.sessions`) come from one per-session-and-group query, a session counting for a group only when that group's register was taken; squad pages (`loadSquad`) use the same rule per child. Families (`/admin/families`) takes `group`, `q` (child or parent name) and `need` (`src/lib/admin/needs.ts`: the To-do steps contacts/payment/contract/consent, plus invite/signin/missing/overdue/check, `missing3` (missed the last 3 sessions, see Missing lately), and `unread`: children with a parent behind on news, `behindOnNews`: 2 or more ack-required messages reaching them through a child in the list's groups, unread, posted since the parent was added; the list then says how many parents, `countBehindOnNews`, which equals the overview's figure), shared with the dashboard's to-do figures and its to-check/overdue/no-plan payment figures, so those always match the list they link to (the overview's "parents not invited yet" counts parents while its link lists their children); phones get cards, `lg` a table. The child page shows this season's contract ("Signed 5 Sep by …" or Not signed). A child opened from the list carries its `group`/`q`/`need` and "← Families" returns to the same list (`src/lib/admin/families-link.ts`: only those keys, each validated, always to `/admin/families`); Send invite and Remove child, which redirect, carry them as hidden fields (`FamiliesFilterFields`, read back by `familiesFilterFromForm`). Admin → Staff can make a coach an admin or an admin a coach (`setStaffRole`, `changeStaffRole` in `src/lib/admin/staff.ts`): never the last admin and never your own role (not offered, like Remove); it and removal (`removeStaffMember`) lock the admin rows first, so two at once can't leave the club with no admin; ticked age groups are cleared either way (admins see every group; a demoted admin coaches every group until their groups are ticked). Staff who are also parents switch sides with a pill at the top of News and Players (`StaffSwitch`: "Club admin" for admins, "Coach tools" to `/coach` for coaches); `/coach` and `/admin` have "Parent view". The news detail's reminder list says "Not set up yet" for a channel without its keys (no VAPID/Twilio/Resend jargon). Read counts on `/admin/news` and its detail are for a group coach's own groups ("Your groups: 1 of 25 read", `groupsOnly` from `loadNewsList`/`loadNewsDetail`), so they agree with the unread list; admins see the whole club. Removing a child (or taking a parent off one) deletes parents left with no children and then, with `asSystem`, their sign-in (`auth.users`; sessions and push subscriptions cascade) and sign-in requests, unless that sign-in is still a parent's or staff's (`src/lib/admin/remove.ts`), as the privacy notice says. Coaches can do everything except import/invite/edit families/manage staff/run the shop (the owner's decision: the shop, its items and prices and order status, including "Transfer received", are admin-only; coaches don't see `/admin/shop`).
- **Chase ladder (`src/lib/chase`):** `ladder.ts` is the engine (pure SQL + injected senders, tested on PGlite): app push at post, email after 24h (at post for `announcements.urgent`, i.e. session cancelled/restored/changed notices), SMS after 48h (Twilio, only if configured), gate flag on the register after 48h. Skips a parent once anyone sharing a child has read it, and never chases a parent about a message posted before they were added (`guardians.created_at`; a new import or sign-up still sees it in News; the gate flag likewise needs one of the child's parents to have been there when it was posted); quiet hours 21:00–08:00 London for every channel, urgent included (an urgent email posted at night goes at the first hourly run after 8am); logged in `announcement_chases` (app/sms/gate unique per parent). Each channel runs in its own savepoint (`tx.savepoint()` on `Queryable`; postgres.js needs its own savepoint API because it fails the whole transaction after any failed statement, even a caught one): a channel that throws is rolled back alone and reported in `failed`, and the rest of the run commits, so reminders already sent stay logged. Senders return only who they reached (push, Resend and Twilio calls time out after 10 s and count as not sent); sign-in links for reminder emails that didn't go are deleted. `senders.ts` holds web-push/Resend/Twilio; `pushToUsers` sends from 10 workers that each take the next device when their last send settles (so one hung push service holds up one worker, not a batch), then writes `last_success_at` and deletes gone (404/410) devices one statement at a time (never parallel queries on one transaction). Runs on posting (`postNews`, in `after()` once the response has gone, as do plan/practice-sheet notifications, so a slow or failing sender never holds up or fails the save; that work runs one task at a time through `enqueue` in `src/lib/background.ts`, which logs failures and never rejects; `drainingSeconds: 60` in `railway.json` gives it time to finish on redeploy) and hourly via `POST /api/cron/chase` (Bearer `CRON_SECRET`) from the Railway cron function `chase-ladder`. `public/sw.js` shows notifications; `NotificationsCard` offers them on Club news; `savePushSubscription` keeps only https endpoints on a known push service, no port or user name (`isPushEndpoint` in `src/lib/chase/push-endpoint.ts`: `fcm.googleapis.com`, `*.push.apple.com`, `updates.push.services.mozilla.com`/`*.push.services.mozilla.com`, `*.notify.windows.com`), so the server never posts to an address someone made up.
- **Attendance QR code (`src/lib/pass`, `src/lib/staff/checkin.ts`; called "pass" in code only):** user-facing copy says "attendance QR code" (parents) and "Scan QR codes" (coaches), never "gate pass" (the owner's wording). one static QR per child (`DSP.<player id>.<HMAC with QR_SECRET>`), swiped between at `/pass` (linked from Friday), so a child who stays home isn't checked in. `/coach` → Scan passes (`PassScanner`, camera + jsQR; the open scanner is its own history entry at the same address, so a phone's Back, Close (`history.back()`, once only: a double tap doesn't leave /coach) and Escape all close it and stay on /coach, and it closes when the page is hidden (phone locked, app switched); focus goes to Close on open and back to "Scan QR codes" after, and the camera stops however it closes) calls `scanPass`, which checks that child into today's session for their age group (method `qr`). The scanner tells apart not a pass, no session today, already checked in and no signal (a failed request, with Try again; never shown as "not a pass"). Rotating `QR_SECRET` cancels all passes (production needs it set; e2e sets a test one). Manual Mark here stays as the fallback. Parents see it: once a child has a check-in at a session that starts today (London; `loadCheckInsToday`), Friday shows "Musa was checked in at 5:58pm" (`CheckedIn`, grass with "Here") in place of the question for that session, and `/pass` shows the same line above the codes. Attendance is taken only on the session's own London day (`registerOpen`, `markHere` in `checkin.ts`): on other days the register shows the next session read-only ("Opens on <day>. You can mark children here on the day.", Mark here and Scan disabled) and `checkInPlayer` refuses; Undo is disabled the same way and `undoCheckIn` refuses too (`undoHere`), so check-ins on other days stay as they are. On a session day, Friday shows today's children's codes in a collapsed "Show attendance QR code" section at the top, and News starts with "<session> today: show the QR code" (`sessionsToday` in `views.ts`). **No signal:** /pass and Friday save each child's QR text, first name and group to localStorage `ds-pass-cache` (`src/lib/pass/cache.ts`, `PassCacheWriter`; one user at a time, replaced on every write; cleared by `SignOutForm` and by the `/sign-in` layout, where every sign-out lands). The parent layout registers `/sw.js` (`RegisterServiceWorker`, no prompt). Its fetch handler touches only navigations to `/pass`, `/friday`, `/news` and `/` (the installed app's `start_url` is /news): network first, and only on failure, or when nothing has come back after 5 s (`NETWORK_WAIT_MS`; a late answer is dropped, and the page's Try again reloads), the static `/offline-pass.html` (no one's data), whose script (`src/offline/pass-page.ts`, bundled with `qrcode` by `scripts/build-offline.mjs`) draws the saved codes. It caches only that page and its script (`ds-offline-v<VERSION>`); everything else passes through. Both files are outside the sign-in proxy. e2e: Playwright's `setOffline` doesn't reach a service worker's own fetches, so `e2e/parent-offline.spec.ts` also aborts every request with a context route. The register (`src/lib/staff/register.ts`, `/coach`) lists every child in the group: "Not here yet (n)", "Said not coming (n)" (still with Mark here; once in they count as here and expected) and "Here (n)" with every check-in (pass or manual) and Undo. Built so the list still to arrive starts on the first screen of a phone even with a dozen flagged children in (e2e checks y < 700 at 390x844): only the last one in gets a card at the top (with Undo and "Needs a word: …"); everyone in who needs a word is one collapsed orange `<details>` summary above Here ("4 children need a word (2 no payment plan, …)", `flagSummary` in `src/lib/staff/flags.ts`, which also holds the flag words shared with the scanner), and each Here row carries its flags as pills; Points and stars / Session plans links sit below the lists. A search box ("Find a child", `RegisterLists`, client-side, `matchesName` in `src/lib/search.ts`: each typed word starts the first name or last initial) filters all three lists instantly; heading counts stay whole. With two or more of the session's groups (that the coach can see) holding children, an "All groups" tab (`group=all`, `ALL_GROUPS`) lists them together by first name, each row with its group pill; Mark here, Undo and flags are the same. A failed page or action shows the club's `src/app/error.tsx` (Try again, no error details).
- **Club shop (`src/lib/shop`, `src/app/(parent)/shop`, `/admin/shop`):** products in `shop_products`; the basket is a cookie of choices only (`basket.ts`); `place_order()` (security definer) prices everything from the table; checkout first runs the same line checks as adding to the basket (`lineProblem`: on sale, size offered, initials allowed, own child) and, if any line fails, takes only those out, names them (a size no longer offered as "Training top (M)") and orders nothing; a failed `place_order` keeps the basket; pass its basket as `$1::text::jsonb` (postgres.js double-encodes a JSON string sent as `::jsonb`, PGlite doesn't). Parents pay by card (SumUp hosted checkout, `sumup.ts`; `confirmSumupPayment` asks SumUp and matches reference + amount, from the order page and `POST /api/sumup/webhook`, and only for a checkout id an order is still awaiting payment on (anything else gets 200 and no call out); both SumUp calls time out after 10 s, which counts as not paid. "Pay" again (`payAgain`) never makes a second checkout for an order (the reference is the order id): if it has one, SumUp is asked; paid confirms it, failed or expired switches the order to bank transfer (`pay_by='bank'`, still awaiting payment, `?switched=bank`, the club gets the new-order email) and the page shows the bank details and reference; pending or no answer changes nothing (`?checking=1`: "We're still checking your card payment. Reload in a minute.") and offers a secondary "Pay by bank transfer instead" (`payByBankInstead`: deactivates the SumUp checkout first, `DELETE /v0.1/checkouts/{id}`, 10 s, best-effort, then switches; the page says a card payment that went through is matched and any double payment refunded); a later card payment on that SumUp page still confirms it and sets `pay_by` back to card. Only an order with no checkout yet gets one, and a refusal switches it to bank too) or bank transfer (`BANK_*` details, reference `DS-XXXXXX`, an admin taps "Transfer received"). No pay on collection. `notifyNewOrder` emails admins (or `SHOP_ORDERS_EMAIL`) once per order. Status: awaiting_payment → paid → ordered → ready (register flag `kit_ready`) → collected, handed out on Fridays. Supplier totals count paid orders only; the table on `/admin/shop` lists the initials to print, and the page links the orders spreadsheet ("Download for the supplier (CSV)"). The parent is emailed once at each step (`notifyParentOrder` in `notify.ts`; migration 0016's `placed_email_at`/`paid_email_at`/`ready_email_at`/`cancelled_email_at`, claimed before sending and cleared if it fails, which is logged; the status change stands either way): order placed (items, total, bank details and reference, or card, "We'll email you when it's ready"), payment received (admin "Transfer received"/"Mark paid", or SumUp confirmed), "Kit ready to collect on Friday", and cancelled. Admin moves, checkout and `confirmSumupPayment` (order page and webhook, also the club's email) send them via `after()` + `enqueue` (inline only outside a request); only a move that happened sends (a repeated tap matches no row). Cancel opens a confirm page (`/admin/shop/orders/[id]/cancel`, plain form; `setOrderStatus` refuses a cancel without `confirm=yes`) that warns a paid order needs refunding separately; it and the notice after say "The parent will be emailed" only when `RESEND_API_KEY` is set (`emailConfigured()`). The parent's order page shows a timeline (`src/lib/shop/timeline.ts`): placed, paid, ready (`ready_at`), collected (`collected_at`), each dated.
- **Shop photos:** the club's kit (from its SumUp shop, photos edited with Runway to show the crest) is seeded by migration 0013 into an empty shop. Photos live in `club_files` (`shop_products.image_file_id`, served by `/api/files`); a link not yet copied in is shown from its link (Items and prices marks it "Photo not copied in"), and `ProductImage` keeps the crest on stripes underneath, shown when there's no photo or it fails to load; a pasted or seeded link is copied in by `localiseProductImages()` (`src/lib/shop/images.ts`) at server start (`src/instrumentation.ts`), on save, and hourly. Admins can also upload a photo. Initials are 2 letters, as on the SumUp shop.
- **Age groups:** the club's groups are U6 (boys and girls), U7, U10 (8–10), U12 (11–12), U15 (13–15) (`AGE_GROUPS`, migration 0005) and Girls (girls of any age, migration 0018; the owner's decision): one group per child, so a girl in Girls isn't also in an age group. ## Design system rules (source: `design/tokens.json`, the Deen Squad design system)

- Never hand-edit `src/app/tokens.css`. Change `design/tokens.json` and run `npm run tokens`. Tailwind classes come from the tokens: `bg-pitch`, `bg-cream`, `bg-paper`, `text-ink`, `text-ink-muted`, `text-grass-text`, `text-gold-text`, `text-kit-orange`, `text-on-pitch`, `rounded-app` (18px, app), `rounded-web` (12px), `rounded-dash` (6px), `rounded-pill`, `shadow-lip-grass`, `font-display`, `text-label`.
- **Surfaces vs text:** `pitch`, `pitch-deep`, `grass`, `crest-gold`, `floodlight` and `kit-orange` fills are surfaces. Text on them uses the matching `on-*` token. Green text on light grounds is `grass-text`, gold text is `gold-text`. Never use `text-pitch`: it fails contrast in dark mode.
- **Colour meanings:** `grass` = done/coming/read. `crest-gold` = achievement. `kit-orange` = needs action (the only signal colour). Every status pill also carries a word.
- **Type:** Bebas Neue (`font-display`) only for headlines, big numbers and shirt numbers. DM Sans for everything that's read.
- **App shapes:** chunky pressable buttons (`btn-chunky btn-grass` / `btn-paper`), cards at `rounded-app` with a 2px `line` border, headers in `pitch` with rounded bottom corners. One primary action per screen. Tap targets at least 48px.
- Mowing stripes (`stripes-v`) only behind headlines and empty image slots, never behind body text.
- Copy: British English, sentence case, address parents as "you", name the child, no emoji, no invented statistics. Prayer times come from a real timetable, never typed by hand.
- Both light and dark themes must pass contrast (4.5:1 text, 3:1 large text). Check both when adding colour.
