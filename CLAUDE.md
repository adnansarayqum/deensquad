# Deen Squad parent app

Mobile web app (installable PWA) for The Deen Squad Football Academy. Parents sign in by email, read club news and tap to acknowledge it, say whether each child is coming to the next session, finish a per-child checklist and follow each child's progress. Coaches use a gate register. Admins import families from a CSV, send invites, post news with read receipts (and chase on WhatsApp), schedule sessions and manage staff. Data lives in Postgres (Railway in production).

| Apply migrations to `DATABASE_URL` | `npm run db:migrate` (Railway runs it before every deploy) |
| Regenerate design tokens | `npm run tokens` |
| Deploy | Push to `main`. Railway (project `deensquad`: services `parent-app` + `Postgres`, both in San Francisco) builds it, runs `scripts/migrate.mjs` at container start (before `next start`; a failed migration fails the health check and the old version keeps serving); settings in `railway.json` override the dashboard; Node is pinned by `engines` in `package.json` to `>=22.13 <23`. Before committing: `npm run typecheck && npm run lint && npm test`, and `npm run test:e2e` when screens or actions change. Stop any running `next start` before `npm run build`; rebuilding under a live server serves mismatched chunks.

## Architecture

- **Database:** `db/migrations/*.sql`, applied in name order, each once (`scripts/migrate.mjs` on Railway, `src/lib/db/migrate.ts` locally). Never edit a migration that has been deployed; add a new numbered file. Both runners set `lock_timeout = '5s'` inside the migration transaction, so a migration that would wait on a busy table fails fast (non-zero exit, nothing applied) and can simply be rerun. Migrations are forward-only (e.g. 0014): to back a feature out, roll back the code, never the migration; undo schema with a new numbered file. `0001_auth.sql` is a Supabase-shaped auth schema (`auth.users`, `auth.uid()`, sign-in requests, sessions). `0002_club.sql` is the club schema with row level security.
- **Security model:** the app connects as the DB owner. `asUser(userId, fn)` (`src/lib/db`) opens a transaction, sets `app.user_id` and `set local role authenticated`, so every policy applies. `asSystem` bypasses RLS and is only for sign-in/sessions/invites. Parent writes that touch `players` or `payment_status` go through security-definer functions (`set_photo_consent`, `report_payment_setup`); the squad headcount comes from `squad_counts()` so parents never read other families' answers. `staff_names` exposes staff names without emails.
- **Multi-child:** `player_guardians` is many-to-many. Parent queries must filter to `my_player_ids()` / the family's age groups explicitly, because a parent who is also staff can read the whole club under RLS.
- **Drivers:** `DATABASE_URL=postgres://` uses postgres.js; `pglite://memory` or `pglite://<dir>` uses PGlite. Both behind `Database`/`Queryable` in `src/lib/db/types.ts`. Cast enums/arrays to text (`::text`, `::text[]`), counts to `::int`, dates to `::text` in selects so both drivers return the same shapes. `DEV_SEED=1` seeds the sample club (refused on Railway).
- **Auth (`src/lib/auth`):** email with a 6-digit code + single-use link (hashed in `auth.sign_in_requests`, 15 min; invites 7 days, link only). The code exists because iPhone home-screen apps don't share cookies with Safari. The link page needs a tap (email scanners). Unknown emails get the same screen and no email. Rate limits per email/IP. Sessions: random cookie `ds_session`, SHA-256 in `auth.sessions`, 90-day sliding. `src/proxy.ts` only does the optimistic cookie check; pages call `requireParent/requireStaff/requireAdmin` (`session.ts`). `ADMIN_EMAILS` creates the first admin on sign-in.
- **Email (`src/lib/email`):** Resend over HTTPS when `RESEND_API_KEY` is set; otherwise an outbox file in dev/tests. In production without a key, only admin sign-in emails are printed to the log (parents' count as not sent). `sendEmails` never throws: it returns `{ sent, failed }` per 100-email Resend batch (10 s timeout, `SEND_TIMEOUT_MS`), so callers must check `failed`. Invites mark `invited_at` (and keep the link) only for parents actually emailed; the admin sees "Sent to N. M not sent – try again later." and a retry reaches only the rest. A failed new-order email clears `notified_at` so the next call retries. The sign-in email leads with the code; the link is the alternative (using either spends both).
- **Parent screens:** `src/app/(parent)/` (news, friday, checklist + contacts/payment/consent, player). Loaders in `src/lib/parent/load.ts`, queries in `data.ts`, pure view builders in `views.ts`, actions in `actions.ts` (call `refresh()` after in-place writes). Forms using `useActionState` keep `action={run}` and add `onSubmit={submitKeepingInput(run)}` (`src/components/submitKeepingInput.ts`): React 19 otherwise clears an uncontrolled form even when the action returns an error. Those forms clear themselves on success (`StatefulForm` after any result without an error).
- **Staff:** `/coach` register (`src/lib/staff`), `/admin` (`src/app/admin`, `src/lib/admin`): CSV import (`import.ts`, preview is a dry run rolled back), invites, news + read receipts + WhatsApp chase (logged in `announcement_chases`), sessions, staff. Layout (`src/app/admin/layout.tsx`): phones get the pitch header with pill nav; at `lg` (1024px) and up a pitch sidebar (`AdminNav layout="sidebar"`) and a `max-w-6xl` main column (forms and detail pages stay `lg:max-w-3xl`). Overview `/admin` is a dashboard (attendance, families and to-dos, payments and shop, news and reminders): all numbers come from `loadDashboard` in `src/lib/admin/dashboard.ts` (one `asUser` transaction, limited to `coachLimit` groups; shop figures for admins only), charts are plain CSS in `src/components/admin/charts.tsx` with numbers in words beside them, and every number links to where it can be acted on. Families (`/admin/families`) takes `group`, `q` (child or parent name) and `need` (`src/lib/admin/needs.ts`: the To-do steps contacts/payment/contract/consent, plus invite/signin/missing/overdue/check), shared with the dashboard's to-do figures and its to-check/overdue/no-plan payment figures, so those always match the list they link to (the Parents bar counts parents while its links list children); phones get cards, `lg` a table. Admin → Staff can make a coach an admin or an admin a coach (`setStaffRole`, `changeStaffRole` in `src/lib/admin/staff.ts`): never the last admin and never your own role (not offered, like Remove); it and removal (`removeStaffMember`) lock the admin rows first, so two at once can't leave the club with no admin; ticked age groups are cleared either way (admins see every group; a demoted admin coaches every group until their groups are ticked). Coaches can do everything except import/invite/edit families/manage staff/run the shop (the owner's decision: the shop, its items and prices and order status, including "Transfer received", are admin-only; coaches don't see `/admin/shop`).
- **Chase ladder (`src/lib/chase`):** `ladder.ts` is the engine (pure SQL + injected senders, tested on PGlite): app push at post, email after 24h, SMS after 48h (Twilio, only if configured), gate flag on the register after 48h. Skips a parent once anyone sharing a child has read it; quiet hours 21:00–08:00 London; logged in `announcement_chases` (app/sms/gate unique per parent). Each channel runs in its own savepoint (`tx.savepoint()` on `Queryable`; postgres.js needs its own savepoint API because it fails the whole transaction after any failed statement, even a caught one): a channel that throws is rolled back alone and reported in `failed`, and the rest of the run commits, so reminders already sent stay logged. Senders return only who they reached (push, Resend and Twilio calls time out after 10 s and count as not sent); sign-in links for reminder emails that didn't go are deleted. `senders.ts` holds web-push/Resend/Twilio; `pushToUsers` sends to 10 devices at a time, then writes `last_success_at` and deletes gone (404/410) devices one statement at a time (never parallel queries on one transaction). Runs on posting (`postNews`, in `after()` once the response has gone, as do plan/practice-sheet notifications, so a slow or failing sender never holds up or fails the save; that work runs one task at a time through `enqueue` in `src/lib/background.ts`, which logs failures and never rejects; `drainingSeconds: 60` in `railway.json` gives it time to finish on redeploy) and hourly via `POST /api/cron/chase` (Bearer `CRON_SECRET`) from the Railway cron function `chase-ladder`. `public/sw.js` shows notifications; `NotificationsCard` offers them on Club news.
- **Attendance QR code (`src/lib/pass`, `src/lib/staff/checkin.ts`; called "pass" in code only):** user-facing copy says "attendance QR code" (parents) and "Scan QR codes" (coaches), never "gate pass" (the owner's wording). one static QR per child (`DSP.<player id>.<HMAC with QR_SECRET>`), swiped between at `/pass` (linked from Friday), so a child who stays home isn't checked in. `/coach` → Scan passes (`PassScanner`, camera + jsQR) calls `scanPass`, which checks that child into today's session for their age group (method `qr`). The scanner tells apart not a pass, no session today, already checked in and no signal (a failed request, with Try again; never shown as "not a pass"). Rotating `QR_SECRET` cancels all passes (production needs it set; e2e sets a test one). Manual Mark here stays as the fallback. The register (`src/lib/staff/register.ts`, `/coach`) lists every child in the group: not here yet, "Said not coming (n)" (still with Mark here; once in they count as here and expected) and "Here (n)" with every check-in (pass or manual) and Undo. A failed page or action shows the club's `src/app/error.tsx` (Try again, no error details).
- **Club shop (`src/lib/shop`, `src/app/(parent)/shop`, `/admin/shop`):** products in `shop_products`; the basket is a cookie of choices only (`basket.ts`); `place_order()` (security definer) prices everything from the table; checkout first runs the same line checks as adding to the basket (`lineProblem`: on sale, size offered, initials allowed, own child) and, if any line fails, takes only those out, names them and orders nothing; a failed `place_order` keeps the basket; pass its basket as `$1::text::jsonb` (postgres.js double-encodes a JSON string sent as `::jsonb`, PGlite doesn't). Parents pay by card (SumUp hosted checkout, `sumup.ts`; `confirmSumupPayment` asks SumUp and matches reference + amount, from the order page and `POST /api/sumup/webhook`) or bank transfer (`BANK_*` details, reference `DS-XXXXXX`, an admin taps "Transfer received"). No pay on collection. `notifyNewOrder` emails admins (or `SHOP_ORDERS_EMAIL`) once per order. Status: awaiting_payment → paid → ordered → ready (register flag `kit_ready`) → collected, handed out on Fridays. Supplier totals count paid orders only.
- **Shop photos:** the club's kit (from its SumUp shop, photos edited with Runway to show the crest) is seeded by migration 0013 into an empty shop. Photos live in `club_files` (`shop_products.image_file_id`, served by `/api/files`); a pasted or seeded link is copied in by `localiseProductImages()` (`src/lib/shop/images.ts`) at server start (`src/instrumentation.ts`), on save, and hourly. Admins can also upload a photo. Initials are 2 letters, as on the SumUp shop.
- **Age groups:** the club's groups are U6 (boys and girls), U7, U10 (8–10), U12 (11–12), U15 (13–15) (`AGE_GROUPS`, migration 0005). The old U9/U11/U13 enum values remain in Postgres but aren't offered. The import maps any age to the group that covers it ("U9" → U10). Phones go through `cleanPhone` (`src/lib/validate.ts`), which also accepts a 10-digit `7xxxxxxxxx` (a mobile whose leading 0 Excel dropped) as `07xxx xxxxxx`.
- **Coach groups:** `staff.age_groups` (set on Admin → Staff; empty = every group). `staffGroups()`/`isGroupCoach()`/`coachLimit()` in `session.ts` limit a coach's register view (today's squads), families list, news audience (no "everyone") and awards to their groups. A group coach also sees only their groups' children (`/admin/families/[id]` 404s otherwise), news whose audience overlaps their groups (list, detail and its unread list, which shows only their groups' parents) and sessions that include one of their groups; they can delete news, cancel/restore/delete sessions and set payment only where every group is theirs (`within`; "everyone" and joint sessions, including the all-groups Friday session, stay with admins: the owner's decision), add sessions only for their groups, and chase on WhatsApp only their groups' parents. Helpers `within`/`overlaps` in `src/lib/admin/scope.ts` (null or empty audience = everyone). Check-in actions (Mark here, pass scanning) stay club-wide (the owner's decision), as do the admin overview counts and exports. Enforced in the app layer, not RLS.
- **Tournament squads (`src/lib/squads`, `/admin/sessions/[id]/squad`, migration 0014):** staff pick which children of a session's age groups play (`session_squads`). A session with any squad rows is a squad session: only picked children's families see it (Friday, upcoming, plan, headcount), answer for it ("Can <child> play in <title> on <day>?", Yes/No stored as coming/away), get its plan notification, and the register lists only the squad; a session with no squad rows works as before, and picking nobody reopens it to the whole groups. Taking a child out deletes their answer for it (`saveSquad`). "Message the squad" posts news with `announcements.squad_session_id` (audience = the session's groups, so coach scope rules still apply): it reaches only the current squad's parents, following later changes, and is deleted with the session. RLS (`is_squad_session`, `in_my_squad`, `squad_allows`) covers sessions, availability, announcements, session_plans and `squad_counts()`; app queries use `sessionIsFor`/`newsReaches` in `src/lib/squads/sql.ts` (parent news/unread, chase ladder, register gate flag, admin read counts (readers who still have a child it reaches, so a squad message's read bar follows squad changes)/unread list, dashboard, WhatsApp chase) and `saveAnswer`/`scanPass` refuse or skip squad sessions a child isn't in. Admins pick for any session; a group coach only for sessions whose groups are all theirs (`within`). The Squad link shows on matches and tournaments (or any session that already has a squad). Season attendance on the dashboard still counts a squad session against the whole group.
- **Self sign-up (`/sign-up`, `src/lib/auth/registration.ts`):** no approval. The details ride on the sign-in request (`auth.sign_in_requests.registration`) and the family is created only when the emailed code/link is used (`finish` → `applyRegistration`); admins get a "New family signed up" email. An existing email just gets new children added by name.
- **Points and stars (`player_awards`, `src/lib/awards`, `/coach/awards`):** coaches (own groups) and admins give a star and/or 1–50 points with a reason, plus coach notes; parents see totals and recent awards on the player screen.
- **Club contract (`src/lib/documents/contract.ts`, `/checklist/agreement`, `agreements`):** the club's player-parent contract text, agreed per child via `sign_agreement()` (security definer, own children only). `CONTRACT.id` names the season; change it to ask everyone again. It's a To-do step; admins see "Contract not signed" on Families. Safeguarding can be added as another document the same way.
- **Session plans and home practice (`src/lib/plans`, `/coach/plans`, `/coach/practice`, `/practice`):** coaches (own groups) and admins write a plan per session per group and post practice sheets, each with an optional PDF or photo (≤ 8 MB, type checked by its bytes in `src/lib/files.ts`). Files live in Postgres (`club_files`, bytea) and are served by `GET /api/files/[id]`, where RLS lets a family open only files on plans or sheets for their groups. Attachments open in the app's own viewer `/files/[id]` (`?from=` the screen it was opened on; same window, never a new tab, because the installed app would open the file full-screen with no way back): pitch header, 48px Back (`router.back()` only when an attachment tap in the app opened it: a sessionStorage marker set by `Attachment` and cleared by the viewer, `src/lib/viewer-marker.ts`; opened any other way it replaces itself with `from` or Friday/Coach) and Download (`/api/files/[id]?download=1`, `Content-Disposition: attachment`). The viewer reads the file with the same RLS query, so anyone who can't open it gets a 404. PDFs are drawn page by page to canvas with PDF.js (`pdfjs-dist` legacy build, loaded only on the viewer; its worker is bundled by `new Worker(new URL(...))`, no CDN; pages draw as they near the screen, at most 2x pixel ratio and 12 MP per page); photos are an `<img>`. A failed fetch says check your signal with Try again and Download; a file PDF.js can't read says it can't be shown here, with Download only (`src/components/files`, helpers in `src/lib/viewer.ts`). Parents see their child's plan and the latest practice sheet on Friday. Server Action body limit is 9 MB in `next.config.ts`.
- **Writing help (`src/components/writing/WritingHelp.tsx`, `src/lib/ai`):** a Dictate button (browser speech recognition, en-GB, free) and, when `ANTHROPIC_API_KEY` is set, "Tidy up with AI" (Claude, `ANTHROPIC_MODEL`, default Haiku 4.5) on news, session plans, practice sheets and coach notes, plus "draft a practice sheet from a session plan". AI only rewrites the text box; staff review and save. Prompts in `prompts.ts` forbid invented facts and surnames, and a muted line under the AI button asks staff for first names only. e2e uses `e2e/fake-claude.mjs` via `ANTHROPIC_API_URL`.
- **Badges:** the club's badges are seeded by migration 0012; coaches (own groups) and admins award or take them back on `/coach/awards/[id]` (`setBadge`).
- **Spreadsheet downloads (`src/lib/exports`, `GET /api/admin/export/[kind]`, admins only):** families and payments, attendance this season (from 1 August), shop orders, points/stars/badges. CSV with a BOM; cells starting = + - @ are defused.
- **Privacy notice (`/privacy`, public):** built into the app and linked from sign-in, sign-up and the player screen; `CLUB_EMAIL` adds a contact address, `PRIVACY_URL` swaps in an external page. Keep it in step with what the app collects and which processors it uses (Railway, Resend, Anthropic, SumUp, push services). Retention periods in it are club policy, not automated.
- **Error alerts (`src/lib/alerts.ts`, `onRequestError` in `src/instrumentation.ts`):** in production, a failed page/action/route emails `ALERT_EMAIL` (default `ADMIN_EMAILS`), at most once per 30 minutes, with the path and message only; a visitor leaving before a page finished loading ("destination stream closed early") is not alerted. Railway itself emails crashes and failed deploys. Backups: Railway's own volume backups need the Pro plan (the project is on Hobby), so the cron service `db-backup` (`backup/`: Dockerfile, `backup.sh`; schedule, root directory `/backup` and restart policy NEVER are set on the service in Railway) runs `pg_dump` nightly at 02:15 UTC into the private Railway bucket `db-backups` (Amsterdam) under `postgres/`, keeps 30 days, proves each dump restores into a scratch database `backup_restore_check` on the same server (row counts compared, then dropped) and emails `ALERT_EMAIL`/`ADMIN_EMAILS` via Resend if any step fails. Restore steps: `backup/RESTORE.md`. Its `pg_dump` must match the server's major version (Postgres 18).
- Tests: `db/schema.test.ts` (RLS as different people), `src/**/*.test.ts` (auth, import, views) on PGlite via `test/db.ts`; `e2e/` signs in with codes from the outbox.

## Next.js 16 notes (this is newer than most training data)

- `cookies()`, `headers()`, `params` and `searchParams` are async. Await them.
- Middleware is now `src/proxy.ts` exporting `proxy()`. Don't create `middleware.ts`.
- `LayoutProps<'/route'>` and `PageProps<'/route'>` are global types generated by `next typegen` (run by `npm run typecheck`). Route-group layouts use an explicit `{ children: ReactNode }`.
- `cacheComponents` is off. Pages that read cookies are dynamic automatically.
- Read `node_modules/next/dist/docs/` before using an API you haven't used here.

## Design system rules (source: `design/tokens.json`, the Deen Squad design system)

- Never hand-edit `src/app/tokens.css`. Change `design/tokens.json` and run `npm run tokens`. Tailwind classes come from the tokens: `bg-pitch`, `bg-cream`, `bg-paper`, `text-ink`, `text-ink-muted`, `text-grass-text`, `text-gold-text`, `text-kit-orange`, `text-on-pitch`, `rounded-app` (18px, app), `rounded-web` (12px), `rounded-dash` (6px), `rounded-pill`, `shadow-lip-grass`, `font-display`, `text-label`.
- **Surfaces vs text:** `pitch`, `pitch-deep`, `grass`, `crest-gold`, `floodlight` and `kit-orange` fills are surfaces. Text on them uses the matching `on-*` token. Green text on light grounds is `grass-text`, gold text is `gold-text`. Never use `text-pitch`: it fails contrast in dark mode.
- **Colour meanings:** `grass` = done/coming/read. `crest-gold` = achievement. `kit-orange` = needs action (the only signal colour). Every status pill also carries a word.
- **Type:** Bebas Neue (`font-display`) only for headlines, big numbers and shirt numbers. DM Sans for everything that's read.
- **App shapes:** chunky pressable buttons (`btn-chunky btn-grass` / `btn-paper`), cards at `rounded-app` with a 2px `line` border, headers in `pitch` with rounded bottom corners. One primary action per screen. Tap targets at least 48px.
- Mowing stripes (`stripes-v`) only behind headlines and empty image slots, never behind body text.
- Copy: British English, sentence case, address parents as "you", name the child, no emoji, no invented statistics. Prayer times come from a real timetable, never typed by hand.
- Both light and dark themes must pass contrast (4.5:1 text, 3:1 large text). Check both when adding colour.
